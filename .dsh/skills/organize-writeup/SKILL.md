# Writeup 组织方法

## 适用范围

适用于根据已有材料创建、更新、纠错和交付题解，也适用于尚未解出的分析记录。输入可以是题面、脚本、实验输出或用户说明，不依赖其他技能及其记录格式。不代替解题流程；不要在缺少证据时为了完成模板而编造解法。

## 工作步骤

1. 首先确保你已经阅读根目录的 AGENTS.md 以及题目相关信息。如果已有上下文无法支撑完整的 Writeup 撰写，调用并发起提问，而不是中止会话。
2. 阅读 `./reference/WRITEUP.md`，按用户语言撰写。保留适用的内容要求，删除无关和空章节；简单题或阶段记录不必套用完整漏洞利用结构。
3. WRITEUP 的语言应当严谨、准确、干练、简洁，易于阅读与复现。鼓励引用 `solve` 文件夹中的文件来代替大篇幅的代码插入引用行为，以提高其易读性。（但严禁滥用，必须在恰当的上下文中执行引用。）

## 证据与状态

- 写作前核对原始发现、候选变换、实际 solver 输出和验证结果。关键结论引用相应文件、提取参数或输出；不能用自己的解释证明自己的假设。
- 长任务进行中可整理证据与正文草稿，最终结果以占位字段保留；验证完成后局部更新结果与相关结论，避免为替换少量字段重写整篇题解。正文未稳定时再调整结构。
- 所有改变原始内容的操作都要解释依据。占位符、作者意图、录入错误等未经验证的解释只能列为假设，不写成成因。
- 排除结论注明实际检查范围。脚本未覆盖的组合、失败和截断的输出，不写成已排除；校验和一致只证明对应数据校验通过，不证明整个答案已找到。
- 分别注明已验证答案、未提交候选、已被否定候选和未解决状态。平台未接受且无其他充分验证时，不写“已解出”“唯一答案”或“完整解法”。用户要求不提交时，明确未提交及现有验证边界。
- 纠错时撤回失效结论及其依据，保留有价值的失败记录；不能只换答案而沿用错误因果链。

## 边界

为了撰写出理想的 WRITEUP，允许提问、复核、纠正错误。

## 完成标准

检查正文与实际运行输出一致、候选变换有依据、验证状态准确、复现路径可用。未解决时明确当前证据、失败候选及剩余问题，不把文档完成写成题目已解出。
